## Why this matters

OpenStory currently exposes runnable component examples, but it does not give a
developer a first-stop documentation reference for a component. The desired
experience is closer to Quasar's component reference: overview, installation,
usage, Foldkit integration, anatomy, styling, keyboard behavior, API,
accessibility, and coverage all visible before examples. This plan adds the
generator and data shape for that first story, proves it with Base UI Avatar,
and keeps the generated story inventory guarded.

Current generated story shape:

```ts
// src/openstory/generated/base-ui-accordion.stories.ts
// Generated by scripts/generate-openstory-stories.mjs. Do not edit by hand.
import type { Meta, StoryObj } from "openstory/foldkit"

import * as AccordionBasicExample from "../../../registry/base-ui/examples/accordion-basic/main"

const meta = {
  title: "base-ui/Accordion",
} satisfies Meta

export default meta

type Story = StoryObj<typeof meta>

export const Basic: Story = {
  name: "Basic",
  render: () => AccordionBasicExample,
}
```

Generator excerpt:

```js
// scripts/generate-openstory-stories.mjs
const renderStory = (story) =>
  [
    line(`export const ${story.exportName}: Story = {`),
    line(`  name: ${JSON.stringify(story.name)},`),
    line(`  render: () => ${story.importName},`),
    line("}"),
  ].join("");
```

Foldkit/OpenStory conventions to follow:

- Generated files under `src/openstory/generated` remain generated. Do not edit
  them by hand; update `scripts/generate-openstory-stories.mjs` and run
  `bun run openstory:generate`.
- A generated story can render a Foldkit program module directly or an object
  returned from a factory, as long as it matches the `openstory/foldkit`
  `StoryObj` render shape.
- Keep docs reference story names stable. The pilot story must be named
  `Documentation`, so its id is `base-ui-avatar--documentation`.
- Use Foldkit conventions from Plan 013 for any new documentation program
  modules: Schema-backed model, messages as facts, `evo()`, and no direct DOM
  mutation.

## Steps

### Step 1: Add the documentation reference data shape and Base UI Avatar data

Create `src/openstory/documentation/referenceData.ts`. It should export:

- `DocumentationSection` types for all required sections.
- `DocumentationReference` with fields for title, lane label, source path,
  registry item name, origin URL, artifact, primitive, install commands,
  usage snippet, Foldkit integration snippet, anatomy x-ray config, styling
  notes, keyboard notes, API rows, accessibility notes, and coverage rows.
- `documentationByItemName`, a readonly record or `Map` keyed by registry UI
  item name.

Add exactly one pilot entry: `base-ui-avatar`.

The `base-ui-avatar` data must include:

- Description/Overview: explain profile image, fallback, group, badge, and count
  scope.
- Installation:
  - `bunx shadcn@latest add @foldkit-cn/base-ui-avatar`
  - `bunx shadcn@latest add https://bearing-ward.github.io/foldkit-basic-cn-ui/base-ui-avatar-basic.json`
- Usage snippet importing from `src/ui/base-ui-avatar`.
- Foldkit integration snippet showing `Submodel.defineView` and parent-owned
  rendering. Because Avatar has no update messages in the basic example, say no
  child commands are expected for the static basic usage.
- Anatomy data from Plan 013, including group, root, image, fallback, badge, and
  count parts.
- Styling notes for exported class hooks:
  `avatarBaseClassName`, `avatarImageClassName`, `avatarFallbackClassName`,
  `avatarBadgeClassName`, `avatarGroupClassName`,
  `avatarGroupCountClassName`, and `avatarSizeClassNameBySize`.
- Keyboard interaction: explicitly state that static Avatar has no required
  keyboard interaction; do not render a separate keyboard section if your
  program treats empty keyboard notes as omitted.
- API rows for `rootView`, `imageView`, `fallbackView`, `view`, `badgeView`,
  `groupView`, and `countView`.
- Accessibility notes for `alt`, fallback text, badge `aria-label`, count
  `role="img"`, and count `aria-label`.
- Existing coverage rows referencing:
  `registry/base-ui/ui/base-ui-avatar/base-ui-avatar.scene.test.ts`,
  `registry/base-ui/examples/base-ui-avatar-basic/base-ui-avatar-basic.scene.test.ts`,
  `scripts/check-openstory-stories.mjs`, and `scripts/smoke-public-site.mjs`.

data.

### Step 2: Add the Foldkit documentation reference program

Create `src/openstory/documentation/referenceProgram.ts`. It should export
`createDocumentationReferenceProgram(reference: DocumentationReference)`.

The returned Foldkit program should render:

- Header with component title, lane label, source path, origin URL, artifact,
  primitive when present, and registry item name.
- Section headings exactly:
  `Description/Overview`, `Installation`, `Usage`, `Foldkit integration`,
  `Anatomy`, `Styling`, `API`, `Accessibility`, `Existing coverage`.
- `Keyboard interaction` only when the reference has non-empty keyboard
  interaction notes.
- The Anatomy section using the `anatomyXray` view from Plan 013.
- Code snippets in `<pre>` or equivalent readable blocks.
- Tables or lists for API and coverage.

Keep the program static except for the x-ray submodel. If the x-ray module from
Plan 013 exposes a full program factory, compose it by reusing its `Model`,
`Message`, `init`, `update`, and `view` through `Submodel`; do not duplicate the
x-ray state machine.

**Verify**:
`bunx vitest run src/openstory/documentation/referenceProgram.scene.test.ts`
should pass after Step 3 adds tests.

### Step 4: Teach the story generator to prepend documentation stories

Update `scripts/generate-openstory-stories.mjs` so a component group can contain
a documentation story before example stories.

Implementation shape:

- Import or otherwise know which registry UI item names have documentation data.
  Prefer exporting a simple `documentationItemNames` set from
  `src/openstory/documentation/referenceData.ts` if Bun can import it in the
  script without TypeScript transpilation trouble. If importing TS from the mjs
  script is brittle, keep a tiny plain JS helper adjacent to the generator and
  document why.
- When creating a group for a component, identify its registry UI item name.
  For the pilot, `base-ui-avatar` should map to group title `base-ui/Avatar`.
- Prepend a story object with:
  - `exportName: "Documentation"`
  - `name: "Documentation"`
  - `kind: "documentation"` or an equivalent explicit discriminator
  - render target `createDocumentationReferenceProgram(baseUiAvatarDocumentation)`
- Keep example story objects distinct, with their existing imports and render
  behavior.
- Update `renderGroup` so generated files import
  `createDocumentationReferenceProgram` and the specific documentation data only
  when the group has a documentation story.
- Preserve existing example story ids. Adding documentation must not rename
  `base-ui-avatar--basic` or `base-ui-avatar--basic-2`.

The generated `src/openstory/generated/base-ui-avatar.stories.ts` should have
the documentation export before example exports:

```ts
export const Documentation: Story = {
  name: "Documentation",
  render: () => createDocumentationReferenceProgram(baseUiAvatarDocumentation),
}

export const Basic: Story = { ... }
```

**Verify**:

`rg -n "Documentation|baseUiAvatarDocumentation" src/openstory/generated/base-ui-avatar.stories.ts`
shows the documentation story before `Basic`.

## Maintenance notes

This plan intentionally pilots one rich documentation reference instead of
generating thin placeholder docs for all components. Reviewers should scrutinize
the data model and generator extension more than the Avatar prose: if those are
clean, future plans can add documentation data for more components lane by lane.
Future rollout should avoid stale docs by sourcing install URLs, registry item
metadata, and example lists from registry data whenever practical, while keeping
human-authored sections for usage, API nuance, accessibility, and x-ray anatomy.
